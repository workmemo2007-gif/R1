# مواصفات تطبيق ممثلي

## 1. تعريف المشروع

**اسم التطبيق:** ممثلي

**نوع التطبيق:** تطبيق ويب متجاوب Mobile-first، قابل للتحويل لاحقاً إلى تطبيق جوال، مخصص لطلاب الشعبة وممثلها والمشرفين.

**الهدف:** توفير منصة موحدة لإدارة الحسابات، التبليغات الرسمية، الجدول الدراسي، المكتبة التعليمية، الملفات الدراسية، الدردشة العامة، الرسائل الخاصة، والإشعارات.

**لغة الواجهة الأساسية:** العربية.

**اتجاه الواجهة:** من اليمين إلى اليسار RTL.

**المستخدمون الأساسيون:**

- الطالب.
- المشرف.
- ممثل الشعبة.
- الممثل الأعلى، وهو حساب ممثل الشعبة المرتبط بالرقم `07723681360` بعد توثيق الرقم في Supabase Auth.

> الممثل الأعلى ليس دوراً منفصلاً بالضرورة في قاعدة البيانات؛ بل هو ممثل شعبة موثق برقم الحساب المحدد، وله تجاوز كامل للصلاحيات.

## 2. الوظائف الرئيسية

### 2.1 الحسابات والتسجيل

كل شخص يدخل التطبيق يجب أن يمتلك حساباً خاصاً به يحتوي على:

- الاسم.
- رقم الهاتف.
- كلمة المرور.
- الصورة الشخصية.
- الدور.
- حالة الحساب.
- تاريخ التسجيل وآخر دخول.

يتم إنشاء الحساب عبر Supabase Auth باستخدام رقم الهاتف وكلمة المرور. لا يتم تخزين كلمة المرور في جدول `profiles`، بل تديرها Supabase Auth.

### حالات الحساب

- `pending`: الحساب بانتظار الموافقة.
- `active`: الحساب فعال ويمكنه استخدام التطبيق.
- `rejected`: الحساب مرفوض.
- `suspended`: الحساب موقوف.

بعد التسجيل:

1. ينشئ المستخدم حساباً برقم الهاتف وكلمة المرور.
2. يضيف الاسم والصورة الشخصية.
3. ينشأ ملفه في جدول `profiles` تلقائياً بحالة `pending`.
4. لا يستطيع استخدام الوظائف الرئيسية حتى تتم الموافقة.
5. يصل إشعار إلى المشرفين أو الممثلين الذين يملكون صلاحية اعتماد الحسابات.

### تسجيل الدخول

- رقم الهاتف.
- كلمة المرور.
- تذكر الجلسة اختيارياً.
- تسجيل الخروج.
- استعادة كلمة المرور من خلال آلية Supabase Auth المناسبة.
- منع الدخول للحسابات المرفوضة أو الموقوفة.

## 3. نظام الأدوار والصلاحيات

### 3.1 الطالب

الصلاحيات الافتراضية المقترحة للطالب:

- مشاهدة الصفحة الرئيسية.
- مشاهدة التبليغات.
- الإعجاب بالتبليغات إذا كانت الصلاحية مفعلة.
- مشاهدة الجدول.
- تصفح المكتبة.
- رفع الملفات الدراسية إذا كانت الصلاحية مفعلة.
- المشاركة في الدردشة العامة.
- إرسال واستقبال الرسائل الخاصة.
- استقبال الإشعارات.
- تعديل معلوماته الشخصية وصورته.

لا يستطيع الطالب افتراضياً:

- اعتماد حسابات.
- اعتماد ملفات.
- تعديل أدوار المستخدمين.
- إدارة المواد أو أنواع الملفات.
- تعديل التبليغات الرسمية.
- تعديل الجدول العام.
- حذف رسائل الآخرين.

### 3.2 المشرف

المشرف هو مستخدم إداري محدود الصلاحيات. يمكن للممثل الأعلى تشغيل أو إيقاف كل صلاحية له.

الصلاحيات الممكنة للمشرف:

- اعتماد الحسابات.
- اعتماد ملفات الطلاب.
- رفع ملفات تحتاج إلى موافقة الممثل.
- رفع الملفات والمشاركة في الدردشة.
- إرسال الرسائل الخاصة.
- إدارة وظائف أخرى فقط إذا منحها الممثل الأعلى صراحة.

ملفات المشرف لا تنشر مباشرة، بل تكون في حالة `pending_representative` وتحتاج إلى اعتماد الممثل الأعلى أو ممثل يملك صلاحية الاعتماد المناسبة.

### 3.3 ممثل الشعبة

الممثل مسؤول عن إدارة التطبيق، وتحدد صلاحياته من الممثل الأعلى. يمكن للممثل الأعلى منح ممثل آخر صلاحيات إدارية محددة.

الصلاحيات الإدارية الممكنة:

- إدارة الحسابات.
- اعتماد الحسابات.
- إيقاف الحسابات وإعادة تفعيلها.
- تعيين أو إلغاء دور المشرف أو الممثل وفق السياسة المعتمدة.
- اعتماد ملفات الطلاب.
- اعتماد ملفات المشرفين.
- إدارة جميع الملفات والمحتوى.
- إدارة المواد.
- إدارة أنواع الملفات.
- إدارة التبليغات الرسمية.
- إدارة الجدول.
- حذف رسائل الدردشة العامة لدى الجميع.
- الاطلاع على سجل العمليات الإدارية.

ملفات الممثل الأعلى تنشر مباشرة، ولا تحتاج إلى موافقة إضافية.

### 3.4 الممثل الأعلى

الحساب الذي يسجل أو يرتبط برقم الهاتف:

```text
07723681360
```

ويكون رقم الهاتف موثقاً في Supabase Auth، مع دور `representative` وحالة `active`.

صلاحياته:

- تجاوز جميع الصلاحيات.
- تشغيل أو إيقاف أي صلاحية لأي مستخدم.
- منح أو سحب الصلاحيات من الطلاب والمشرفين والممثلين.
- إدارة الحسابات والمحتوى بالكامل.
- تغيير أدوار المستخدمين.
- اعتماد الحسابات والملفات.
- الاطلاع على سجل العمليات.
- إدارة المواد وأنواع الملفات والجدول والتبليغات.

لا يستطيع أي مستخدم تعديل دوره أو صلاحياته بنفسه.

## 4. الصلاحيات القابلة للتشغيل والإيقاف

تظهر للممثل الأعلى في صفحة إدارة المستخدمين، مع مفتاح تشغيل/إيقاف لكل صلاحية:

- `approve_accounts`: اعتماد الحسابات.
- `approve_student_files`: اعتماد ملفات الطلاب.
- `approve_supervisor_files`: اعتماد ملفات المشرفين.
- `upload_files`: رفع الملفات.
- `public_chat`: الدردشة العامة.
- `private_messages`: الرسائل الخاصة.
- `like_announcements`: الإعجاب بالتبليغات.
- `manage_accounts`: إدارة الحسابات.
- `suspend_accounts`: إيقاف الحسابات.
- `manage_subjects`: إدارة المواد.
- `manage_file_types`: إدارة أنواع الملفات.
- `manage_content`: إدارة المحتوى.
- `manage_announcements`: إدارة التبليغات.
- `manage_schedule`: إدارة الجدول.
- `delete_public_messages`: حذف رسائل الدردشة العامة.
- `view_audit_logs`: الاطلاع على سجل العمليات.

تطبيق الصلاحيات يكون في قاعدة البيانات عبر RLS، وليس بمجرد إخفاء الأزرار في الواجهة.

## 5. هيكل التصفح العام

### 5.1 شريط التنقل السفلي في الجوال

يظهر شريط تنقل ثابت أسفل الشاشة يحتوي على:

1. الرئيسية.
2. المكتبة.
3. الدردشة.
4. الإشعارات.
5. الحساب.

في الشاشات الكبيرة يمكن تحويله إلى شريط جانبي أو شريط علوي.

### 5.2 الصفحة الرئيسية

تحتوي الصفحة الرئيسية على:

- تحية باسم المستخدم وصورته.
- حالة الحساب إذا كان بانتظار الموافقة.
- شريط بحث اختياري.
- بطاقات مربعة رئيسية:
  - الجدول.
  - التبليغات.
  - المكتبة.
  - الدردشة العامة.
  - الرسائل الخاصة.
  - الإشعارات.
- آخر التبليغات.
- أقرب محاضرة أو عنصر في الجدول.
- آخر الملفات المضافة.
- اختصارات إدارية للمستخدمين الإداريين.

### 5.3 صفحة الحساب الشخصي

تحتوي على:

- الصورة الشخصية.
- الاسم.
- رقم الهاتف، مع منع تعديله دون إجراء تحقق.
- الدور الحالي.
- حالة الحساب.
- تاريخ التسجيل.
- تعديل الاسم.
- تغيير الصورة.
- تغيير كلمة المرور.
- تسجيل الخروج.

للمستخدم الإداري تظهر أيضاً:

- الصلاحيات المفعلة.
- الصلاحيات الموقوفة.
- سجل النشاط الشخصي إن لزم.

### 5.4 صفحة الإدارة

تظهر للمستخدمين الذين يملكون الصلاحيات المناسبة فقط:

- الحسابات الجديدة.
- الحسابات الفعالة والموقوفة.
- الملفات بانتظار الاعتماد.
- إدارة المواد.
- إدارة أنواع الملفات.
- إدارة التبليغات.
- إدارة الجدول.
- سجل العمليات.
- البحث والتصفية.

- عرض أسبوعي.
- عرض يومي للجوال.
- اسم المادة.
- اسم المحاضر اختيارياً.
- وقت البداية والنهاية.

- ملاحظات.

## 8. المكتبة التعليمية

### بنية المكتبة

المكتبة مقسمة إلى:

1. المواد.
2. أنواع الملفات داخل كل مادة.
3. الملفات المنشورة.

الأنواع الافتراضية:

- ملخص.
- ملزمة.
- محاضرة.

يمكن للممثل الذي يملك `manage_file_types` إضافة أنواع جديدة، مثل:

- أسئلة سنوات.
- مراجعة.
- واجب.
- مصادر خارجية.
- تسجيلات.

### خصائص المكتبة

- البحث باسم الملف.
- التصفية حسب المادة.
- التصفية حسب نوع الملف.
- ترتيب الأحدث أو الأكثر استخداماً.
- فتح الملف أو تنزيله.
- عرض اسم الرافع وتاريخ النشر.
- إظهار حالة الملف للمشرفين والإداريين.

## 9. رفع الملفات واعتمادها

### مسار رفع الملف

1. يضغط المستخدم على رفع ملف.
2. يختار المادة بشكل إجباري.
3. يختار نوع الملف بشكل إجباري.
4. يكتب عنوان الملف.
5. يختار الملف من الجهاز.
6. يرسل الطلب.
7. يحفظ الملف في Storage.
8. يحفظ سجل الملف في `study_files`.
9. يحدد النظام الحالة حسب الدور:
   - الطالب: `pending`.
   - المشرف: `pending_representative`.
   - الممثل الأعلى: `published`.
10. يصل إشعار للمستخدم صاحب صلاحية الاعتماد.

### اعتماد الملف

- الموافق يستطيع مشاهدة قائمة الملفات المعلقة.
- يستطيع فتح الملف ومعاينته أو تنزيله.
- يختار اعتماد أو رفض.
- عند الاعتماد تصبح الحالة `published`.
- عند الرفض تحفظ ملاحظة الرفض.
- يسجل القرار في `file_reviews` و`audit_logs`.

### التخزين

- `avatars`: للصور الشخصية.
- `study-files`: للملفات الدراسية، وهو bucket خاص.
- يتم استعمال Signed URLs للملفات الخاصة.
- اسم مسار الملف يبدأ بمعرف المستخدم حتى يمكن تطبيق سياسات التخزين.

## 10. الدردشة العامة

### الخصائص

- جميع الحسابات الفعالة تنضم تلقائياً.
- إرسال نصوص قصيرة.
- إظهار اسم وصورة المرسل.
- وقت الرسالة.
- دعم التمرير والتحميل التدريجي.
- Realtime لظهور الرسائل فوراً.
- لا توجد صلاحية رفع ملفات داخل الدردشة العامة حسب المتطلب الحالي.
- حذف الرسائل تلقائياً بعد 24 ساعة.
- الممثل الذي يملك `delete_public_messages` يستطيع حذف رسالة لدى الجميع.

### الرسائل المؤقتة

يعمل Cron كل ساعة ويستدعي دالة حذف الرسائل الأقدم من 24 ساعة لتقليل الضغط على قاعدة البيانات.

## 11. الرسائل الخاصة

### الخصائص

- البحث عن مستخدم فعال.
- بدء محادثة خاصة.
- قائمة المحادثات.
- عدد الرسائل غير المقروءة.
- إرسال واستقبال الرسائل فورياً عبر Realtime.
- إظهار حالة آخر ظهور اختيارياً.
- منع إرسال الرسائل للحسابات الموقوفة.
- لا يمكن قراءة رسالة خاصة إلا من أعضاء المحادثة.

الجداول الأساسية:

- `conversations`.
- `conversation_members`.
- `private_messages`.

## 12. الإشعارات

### الإشعارات داخل التطبيق

تصل عند:

- قبول الحساب أو رفضه.
- إيقاف الحساب.
- نشر تبليغ رسمي.
- نشر ملف مرفوع.
- رفض ملف مع الملاحظة.
- وصول رسالة خاصة.
- اقتراب موعد دراسي إذا تم تفعيل ذلك لاحقاً.

### الإشعارات خارج التطبيق

لإرسال Push Notifications حتى عند إغلاق التطبيق:

- يوافق المستخدم على الإشعارات.
- تحفظ بيانات الجهاز في `push_subscriptions`.
- تستخدم Edge Function أو خدمة Push لإرسال الإشعارات.
- تحفظ نتيجة الإرسال في سجل مناسب عند الحاجة.

- لا توضع كلمة مرور PostgreSQL في GitHub.
- كل صلاحية حساسة تتحقق منها RLS في Supabase.
- كل عملية إدارية تسجل في `audit_logs`.
- تستخدم Signed URLs للملفات الخاصة.
- يتم فحص نوع وحجم الملفات قبل الرفع.
- لا يعتمد النظام على إخفاء الأزرار وحده.

### مراحل البرمجة

1. تجهيز مشروع GitHub.
2. إنشاء هيكل الواجهة RTL.
3. ربط Supabase Auth.
4. بناء التسجيل والدخول وحالة انتظار الموافقة.
5. بناء الصفحة الرئيسية والتنقل.
6. بناء الجدول والتبليغات.
7. بناء المكتبة ورفع الملفات والاعتماد.
8. بناء الدردشة العامة مع Realtime والحذف التلقائي.
9. بناء الرسائل الخاصة.
10. بناء الإشعارات.
11. بناء لوحة الإدارة والصلاحيات.
12. اختبار RLS والصلاحيات بأدوار مختلفة.
13. اختبار الجوال والشاشات الكبيرة.
14. نشر نسخة تجريبية.
15. ربط المستودع والنشر النهائي بعد الاعتماد.

## 17. قواعد مهمة قبل بدء البرمجة

- لا يتم إنشاء مستخدم إداري من الواجهة دون اعتماد.
- لا يتم منح صلاحيات مباشرة من المتصفح دون تحقق RLS.
- الممثل الأعلى فقط يستطيع تغيير الأدوار والصلاحيات.
- ملفات الطلاب والمشرفين لا تظهر في المكتبة العامة قبل اعتمادها.
- رسائل الدردشة العامة مؤقتة وتحذف بعد 24 ساعة.
- الرسائل الخاصة لا يقرأها إلا أعضاء المحادثة.
- التبليغات الرسمية يمكن إرسالها لجميع الحسابات الفعالة.
- يتم تسجيل التعديلات الإدارية المهمة.
- يمكن تعديل المخطط لاحقاً من خلال Migrations دون حذف البيانات الحالية.

## 18. حالة المشروع الحالية

تم تجهيز قاعدة البيانات الأساسية على Supabase، بما في ذلك الجداول والعلاقات والصلاحيات وRLS وStorage وRealtime وCron.

المرحلة التالية هي بناء واجهة التطبيق وربطها بهذه الجداول، ثم اختبار كل دور وصلاحية قبل النشر.

هذه الوثيقة هي المرجع الأولي للبرمجة، ويمكن تعديلها مع ظهور متطلبات جديدة أثناء بناء التطبيق.
